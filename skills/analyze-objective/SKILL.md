# 目的に沿った分析

問いに答える最小の比較を選び、その根拠を残す。
保存の構成とテンプレートは [workspace.md](../../references/workspace.md) を読む。
目的と知見の管理は [$manage-objective-knowledge](../manage-objective-knowledge/SKILL.md) の規則に従う。

## 分析のHowを組み立てる

- 利用先の `AGENTS.md` と現在の目的の三つの管理ファイルを読む。関連する知見の適用条件を照合する。新しい目的での実行なら目的フォルダを作る。
- 何を知りたいか、何がわかれば判断が変わるかを一文にする。必要に応じて仮説と対立説明を置く。探索では比較軸を明確にする。
- 母集団、期間、観測単位、指標と分母、取得時点、除外条件を定める。結論を変える不足情報だけまとめて確認し、通常の選択は仮定を明記して進める。
- 最初の集計・図・baseline、比較条件、結果の読み方を選び、なぜその方法で問いに答えられるか説明する。手法名の一覧で終えない。
- 問いに答えたら止める。判断不能で止める条件と、そのとき必要な追加情報を決める。全項目を形式的な計画書へ展開しない。

| 問い | 最初の比較 | 結論を左右する確認 |
|---|---|---|
| 何が起きたか | 件数・率・分布の推移と内訳 | 分母、定義変更、欠測・遅延 |
| どこで差が出たか | 共通軸の差分と層別集計 | 母集団構成、標本数、比較可能な範囲 |
| なぜ起きたか | 対立説明を識別する比較 | 交絡、選択過程、時間順序 |
| どちらがよいか | 同じ評価条件でbaselineと比較 | リーク、公平な調整、不確実性、運用上の差 |

設計だけの依頼なら実行可能な手順まで返し、分析実行や記録を始めない。

## 実行して根拠を確認する

1. 利用先で指定されたPython・SQL・Notebook等の実行環境と、データアクセス・保存規則を使う。既存skillやツールがあるなら利用する。このpluginだけのためにCLI、Papermill、Polarsを導入しない。
2. `analyses/<記録ID>/record.md` に問い、計画、仮定を記録する。入力の所在・識別子・期間、抽出条件、主要パラメータ、コードと実行方法を追跡できるようにする。データ本体を記録フォルダへ複製することは必須にしない。
3. 必要な範囲で行数、型、単位、キー、重複、欠損、時間範囲を確認する。小さな集計やbaselineで現象を確かめてから複雑な分析へ進む。
4. コードは入力から出力まで追える形にする。意味のないhelperやclass、不要な旧Python互換処理を追加しない。サポートバージョンとライブラリの書き方は利用先に合わせる。Polarsでは利用先の方針と両立する範囲でnamed expressionを優先する。
5. 重要な結論を支える実際の表・図・数値を確認する。コードの正常終了だけで妥当としない。観測単位、分母、抽出条件、代表値など、問いに関わる意味的な検証を行う。テストは主要な契約やリスクを守る必要十分なものを選び、集計コードの言い換えだけのテストを増やさない。
6. 時系列や予測では情報の利用可能時点とリークを確認する。反復観測の依存関係、選択バイアス、小標本など、結論を変え得る条件に絞って不確実性を扱う。記述比較だけで因果や未観測集団の性能を断定しない。
7. 観測結果、解釈、限界、未実行事項、次の判断を記録する。失敗・否定・判断不能も有用なら残す。未提供データから数値を作らない。

## 結論と知見を更新する

- 実行済みの試行に対応するコード・条件・結果を保持する。結論に影響する再分析は新しい記録IDにし、前の結果を上書きしない。表現の訂正は根拠を変えず行ってよい。
- 元データや大きな生成物の保存は利用先の規則に従う。共有する結論には、確認可能な分析記録や必要最小限の表・図を参照させ、消える一時ファイルだけを根拠にしない。
- `$manage-objective-knowledge` の手順で個別知見、`CURRENT_STATE.md`、必要なら `KNOWLEDGE_INDEX.md` を更新する。`DESCRIPTION.md` は通常の分析更新では変更しない。
- 問いへの答え、主要な根拠、実行済みか設計のみか、重要な限界、次の判断、記録へのリンクを短く返す。
